# 002 — The phone as a tool: MCP over the panel

**Opened 2026-08-28, on the user's call**: *"the current debug and testing approach is inefficient — let us
make an MCP server, so you connect to my phone and have full access to testing the whole project in the
browser and in Termux."*

The complaint is right and the arithmetic says so. Every device-gated number this project owes — the field
run, the residency ceiling, the mode-switch cost, the tile bake, the baked-3D comparison — currently travels
as: an agent writes code → a person taps a panel → a person reads a screen → a person types back what it
said. Each round trip is a message, several minutes, and **whatever detail nobody thought to copy**. The
panel already removed the worst of it (a run is a tap, a capture is a commit). What is left is that the agent
cannot see any of it.

## What this is, and what it deliberately is not

**It is a CLIENT of the running panel, never a second copy of it.** `JobRunner` allows one job at a time, and
two runners on one phone is two converts fighting over one folder — the exact failure the panel's own
one-at-a-time rule exists to prevent. So `mcp.mjs` speaks to `http://127.0.0.1:8787` and, when the panel is
not up, says so instead of starting anything.

**What it can do is what the panel's buttons can do.** The jobs are an allowlist (`jobs.mjs`), not a shell:
preflight and state, the three converts, the pull/setup rituals, the shareable build, the log, the stop, and
`commit & push` over what the map itself filed. An agent that can do those can drive the whole measurement
loop without a person relaying a screen.

| Tool | What it answers |
| --- | --- |
| `phone_state` | the 15 preflight checks and their verdict, the pak and its recipe, the running job, the ports, the captures waiting to be committed |
| `phone_jobs` | the allowlist itself — read from the table `buildJob` validates against, never a list kept in step by hand |
| `phone_run` | start one, with its knobs; refused while another runs |
| `phone_log` | the tail of the same ring the page shows — one log, or a field report and the screen disagree |
| `phone_stop` | stop it |
| `phone_commit` | commit and push exactly what the panel says is pending |

## The shell tool, and why it is off

`phone_exec` runs a command in the repository, and it is **off unless `PANEL_MCP_EXEC=1`**. The user asked
for full access and this is how full access is given: as something switched on deliberately, on the day it is
wanted, rather than as a remote shell that arrives with an update. The allowlist covers the measurement loop;
`exec` covers what nobody anticipated, which is a real category and not one to pretend away.

## Two transports, one handler

- **stdio** (default) — a Claude running ON the phone, in Termux. Nothing is exposed to any network at all.
- **`--http --port 8788`** — JSON-RPC over POST, for a Claude that is somewhere else. Binds `127.0.0.1` like
  the panel, and **requires a bearer token** (`PANEL_MCP_TOKEN`, or one generated and printed at startup).

**Reaching it from off-device is a tunnel the operator sets up on purpose**, and the token is what makes that
survivable: a tunnel plus no token is a shell on the open internet, addressed by a URL that is guessable the
moment it is logged anywhere. This is the one part of the design that is a security decision rather than an
engineering one, and it belongs to whoever owns the phone.

## What is verified, and where

The protocol and the plumbing are testable without a phone, and were: `mcp.test.mjs` covers the handshake,
the tool list, the notification-has-no-reply rule, the difference between a JSON-RPC error and a tool
failure (an agent can act on the second and can only give up on the first), the shell tool's default-off, and
that a run goes THROUGH the panel. Beyond the unit tests, the whole path was exercised in a container on
2026-08-28: `initialize` → `tools/list` → `phone_state` (15 checks, verdict `fail` — correctly, there are no
game files there) → `phone_run districts` → `phone_log`, which returned the district table the job printed.

**What a container cannot verify** is the part that is the point: that a phone behind a tunnel answers, and
that Claude Code's own MCP client is happy with this handshake. MCP servers are read from `.mcp.json` at
session start, so the first session to use it is the first proof.

**Two things the first attempt got wrong, both found on a real phone the same day (2026-08-28):**

- **The tunnel.** cloudflared's own pre-check failed both ways — `QUIC connection failed` and `HTTP/2 is
  blocked` — while `api.cloudflare.com:443` passed: the carrier allows 443 and blocks **7844**, the only
  port cloudflared uses in either protocol. Nothing in its config reaches that, so `tunnel.mjs` now tries
  every installed provider in an order chosen by what survives a restrictive network — **ngrok** (443, needs
  a free account), **pinggy** and **serveo** (SSH asked for 443, no account), **localhost.run** (SSH),
  **cloudflared** last — falling through by name. `TUNNEL=<name>` forces one.
- **An address is not a tunnel.** The first version announced on the address line, and cloudflared prints
  `Your quick Tunnel has been created!` BEFORE it has dialled the edge: it printed one, failed every dial
  after it, and the paste block claimed a dead URL was ready — worse than printing nothing. A provider is
  now announced only once it says it is connected, and one whose own pre-check reports `hard_fail=true` is
  dropped on that line instead of after the timeout. Both paths were replayed through the runner with the
  phone's verbatim log lines.
- **The config.** `"url": "${OPENSA_PHONE_URL}"` is refused whole when the variable is unset — Claude Code
  leaves an unset `${VAR}` unexpanded and reports `INVALID_CONFIG: 'url' is not a valid URL`; `${VAR:-default}`
  did not help either. That failure is at **load**, so it costs a new session to clear. `.mcp.json` now runs
  `mcp-bridge.mjs`, a stdio server that reads the address and token at run time and forwards each call over
  HTTP. The session always loads: without the variables it lists no tools and says what to set, with them it
  is the phone's tool list. `mcp-bridge.test.mjs` covers both sides, plus a rejected token reported as itself
  rather than as a stale address.

## The browser half, and why it is not a browser protocol

**Landed 2026-08-27 with the rest.** The ask was explicit: not just the panel, but the map page — see it,
read its numbers, its realtime benchmarks, drive it. Two ways to do that, and the cheap one turned out to be
the better one:

| | Chrome DevTools Protocol | The page as the instrument |
| --- | --- | --- |
| needs | `adb`, developer options, a wireless-debugging pairing, a port forward | nothing |
| sees | any page, including one whose bundle failed to parse | our console, once it boots |
| reads | the DOM, the console, arbitrary JS | the inventory report, the readout, the error log, the board |
| pictures | a real screenshot of the device | the console's own `exportImage` composition |

The console already computes everything worth reading (that is what `?inventory=1` is) and already composes
its own PNG (that is what 201/7-07's share link is). So the page long-polls the panel for commands and
answers them: `snapshot`, `screenshot`, `pose`, `mode`, `ops`, `errors`. `MapBus` is the queue, one waiter
per command, and it says WHICH end went quiet — "no map is attached" and "the map took it and never
answered" are different problems and a caller must not have to guess.

**Opt-in by query.** `&agent=1` is on the panel's own links and nowhere else, so a shared link on somebody
else's phone never talks to a local port that happened to answer.

**What this cannot do, stated rather than discovered:** a page that fails to load at all cannot report that
it failed. The boot shell and the error log cover a boot that gets far enough to run; a bundle that does not
parse is invisible to this channel and visible to CDP. That is the case CDP earns its prerequisites for, and
the reason it stays on the list below rather than being crossed off.

Verified end to end in a container on 2026-08-28, with a stand-in page: `map_state` (attached, with the
heartbeat), `map_snapshot` (the report came through), `map_screenshot` (an MCP **image** block, not a base64
string the agent would have to describe), `map_mode` and `map_goto` (the page acted and answered).

## Next, and in this order

1. **CDP, for the one thing the page cannot do**: report that it failed to load. `adb` over wireless
   debugging plus `adb forward tcp:9222 localabstract:chrome_devtools_remote` gives navigation, console and
   a device screenshot of any page — worth it the first time a bundle breaks on the phone and the channel
   above goes silent, and not before.
2. **A scripted run.** The console can already drive itself (`?bake=tiles` does). A `?script=` that flies a
   named path and files its capture would make "take the field measurement" one tool call, with no browser
   protocol at all — worth costing against the CDP route before building either.
